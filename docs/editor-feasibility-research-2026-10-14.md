# 静读 Markdown 编辑功能实现难度调研

调研日期：2026 年 10 月 14 日。用途：交给 GPT Pro 评估实现成本与长期维护负担，决定是否为静读加入编辑功能。

目标是让静读的日常写作体验达到 Obsidian 基础编辑能力加部分输入增强的水平。输入增强作为产品内置能力；不开发 Obsidian 插件，不做插件市场，也不要求加载现有 Obsidian 插件。

目前最有依据的判断是：保留现有阅读器、使用文本编辑内核承载编辑和源码两种模式，方向可行；但实时预览的输入稳定性、草稿与文件同步，以及公式输入增强会构成持续维护工作。现成库能减少部分工作，不能据此认定“简单接入即可达到 Ob 的体验”。Ob 已支持打开 vault 外的 Markdown，进一步提高了自行开发所需的收益门槛。

## 1 用户需求和评估边界

用户主要从空白开始写较长的中文学习记录，也要修改已有笔记。记录涉及公式、代码、截图、列表等，分散在不同阶段和项目的文件夹中，不希望为每个文件夹建立和维护笔记仓库。用户更喜欢静读当前的阅读外观。

讨论中形成的界面方案如下：

| 模式 | 用户期望 |
| --- | --- |
| 阅读 | 与当前静读的排版和操作完全一致，包括高亮、图片、公式、折叠、大纲和阅读位置 |
| 编辑 | 对标 Ob Live Preview：直接在排版后的正文中输入，光标进入相应内容时露出必要语法 |
| 源码 | 完整显示 Markdown，能够精确修改复杂结构 |

打开已有文件默认阅读；新建笔记进入编辑是此前提出的默认方案。三种模式处理同一份内容，切换不丢修改和撤销历史。阅读与编辑可以使用不同的视图实现，编辑与源码应尽量共用编辑状态。

“Ob 基础能力”不能仅解释为输入文字和隐藏 Markdown 标记，也不等于完整重建 Ob 产品。后续应逐项确认实际使用能力，尤其是表格、双链建议、公式片段和图片操作的深度。本报告中的范围拆分用于估算，不代表用户已经接受删减能力。

短期原型和自动化测试不能证明长期写作体验可靠。此次提供文档证据、现有架构和风险分解；没有运行候选编辑器，没有测量包体、内存、输入延迟，也没有证明插件在 Ob 外部文件中的兼容性。

## 2 Ob 单文件支持已改变比较前提

Obsidian 在 2026 年 10 月 5 日发布的桌面公开版 1.14 中支持打开 vault 外的 Markdown；文件进入当前窗口，本地图片和链接按 Markdown 所在目录解析，提供大纲和外链导航。系统“打开方式”集成要求安装新版安装器。[官方发布说明](https://obsidian.md/changelog/2026-10-05-desktop-v1.14.4/)

这意味着不能再把“Ob 只能处理 vault 内文件”作为开发静读编辑功能的核心理由。仍需分别确认：外部笔记中新插入截图的实际保存目录、所需输入增强在外部文件中的行为，以及编辑外部文件时采用哪一套设置。单文件支持本身不证明每个插件及附件工作流都符合用户需要。

Ob 的 Live Preview 是编辑视图中的一种模式；另一种是源码模式。它隐藏大部分语法，光标进入格式内容后显示底层语法。这里的“编辑模式”对应 Live Preview。[官方模式说明](https://obsidian.md/help/edit-and-read)

图片操作的比较基准也需要更新：Ob 1.13 已增加 Live Preview 中图片的键盘选中、复制剪切删除、调整大小和进入编辑等操作。不能把这些一律算成需要插件补充的能力。[1.13 官方发布说明](https://obsidian.md/changelog/2026-07-30-desktop-v1.13.4/)

## 3 静读当前架构和接入成本

以下事实来自当前本地工作树。工作树存在未提交的既有改动，因此本报告描述的源文件不保证与某个已发布二进制完全相同。

源码仓库：[Ray8mu34/JingduMD](https://github.com/Ray8mu34/JingduMD)。建议优先查看[当前开发分支 codex/reading-reliability-typography](https://github.com/Ray8mu34/JingduMD/tree/codex/reading-reliability-typography)。

2026 年 10 月 14 日核对远端时，GitHub 主分支为 0.9.1，开发分支为 0.9.3（提交 `8fde994`），本地工作目录为 0.9.5。当前本地图片、高亮等改动及本报告尚未提交上传。架构描述以本报告中的本地状态为依据；GitHub 源码用于辅助核查。若远端与本报告不同，请先区分版本差异，不要直接把远端旧行为判断为本地现状。

| 层次 | 当前事实 | 对编辑功能的影响 |
| --- | --- | --- |
| 桌面运行时 | Tauri 2、Rust；Windows WebView2，macOS WKWebView | 可以加入网页编辑内核，但剪贴板、拖放、文件写入和平台差异仍需宿主适配 |
| 前端 | React 18、TypeScript、Vite；当前依赖没有 CodeMirror 或 ProseMirror | 需要新增编辑内核和集成层，不能直接给现有组件加一个开关完成 |
| 阅读渲染 | ReactMarkdown、remark/rehype、KaTeX、Mermaid、highlight.js，以及自定义语法处理 | 可保留阅读器；编辑器需要另一套语法树和显示机制，两者要保持语义兼容 |
| 图片 | Rust 读取本地资源，远程图片有现有访问规则；支持阅读缩放和预览 | 可复用资源读取与访问规则；图片插入、保存和编辑器内预览是新增能力 |
| 文件写入 | write_file_highlights 仅允许改变高亮语法，不允许改写正文；有备份和保存前校验 | 不能当通用正文保存接口使用；需要新增通用保存能力并保留高亮接口的原有约束 |
| 文件监听 | 当前 external-change 会重新加载打开的文档 | 有未保存修改时必须改成按状态处理，不能直接覆盖草稿 |
| 标签页 | ReaderWorkspace 用 App key={active} 渲染当前标签；切换会重建 App | 草稿、选区、撤销栈需要由标签页文档会话持有，不能只放在当前 App 内 |
| 多窗口 | 已有独立窗口和标签会话；高亮写入在应用内串行 | 普通编辑需要处理同一文件多窗口修改、保存版本和跨窗口通知 |
| 长文 | 当前阅读优化含 content-visibility、重组件延迟显示 | 阅读优化不能直接证明输入性能；需要编辑内核的增量处理和编辑组件缓存 |

关键源码入口：

- `package.json`、`src-tauri/Cargo.toml`：技术栈和依赖。
- `src/ReaderWorkspace.tsx`：标签页生命周期与当前页面重建。
- `src/App.tsx`：文档加载、外部变更监听、高亮保存和阅读状态。
- `src/components/MarkdownReader.tsx`：阅读管线、公式、图片和组件显示。
- `src/lib/markdown.ts`：公式分隔符处理、frontmatter、大纲、callout、wikilink。
- `src/lib/fileHighlights.ts`、`src-tauri/src/file_highlights.rs`：源码高亮、偏移映射与受限写入。
- `src-tauri/src/lib.rs`：读文档、读资源、路径约束、编码和文件监听。
- `docs/typography-contract.md`、`docs/highlights.md`、`DESIGN.md`、`UX-CONTRACT.md`：现有排版和行为依据。

还有两个与文件保真直接相关的事实：

1. 阅读前会做公式分隔符转换及高亮预处理。编辑器应持有原始 Markdown，不能拿阅读时转换后的字符串作为写回依据。
2. 现有读取支持 UTF-8、带 BOM 的 UTF-8、UTF-16 和 GBK 回退；高亮写入保留 BOM/UTF-16，但无 BOM 的其他编码按 UTF-8 写出，文档明确 GBK 加入颜色圆点后转换为 UTF-8。新增通用保存不能默认为所有原编码都已经可往返保留。

## 4 需要估算的能力清单

下表的难度是结合当前架构作出的工程初评，不是实测工时。低：成熟内核通常可提供主要机制；中：需要宿主或语法适配；高：多状态、多组件或跨平台行为需要持续打磨。多个“中”能力组合后也可能形成高成本。

| 能力 | 具体操作或边界 | 初评 |
| --- | --- | --- |
| 普通文本编辑 | 中文输入、选词、删除、撤销重做、选区、长段落、换行、剪贴板 | 中；IME 和预览装饰交互是重点 |
| Markdown 常用快捷操作 | 粗体、斜体、行内代码、标题、链接；有选区和无选区时行为一致 | 中；内核命令仍需适配 Markdown 语义 |
| 列表和引用 | Enter 续写、空项退出、Tab/Shift+Tab 缩进、任务项、引用中粘贴多行 | 中；混合嵌套是主要边界 |
| 实时预览基础格式 | 标题、强调、删除线、引用、列表、分隔线；按光标/选区显露语法 | 高；隐藏标记后的选区与输入不能错位 |
| 代码块 | 缩进、Tab、语言、语法高亮；代码中的 Markdown 字符保持原义 | 中 |
| 图片插入 | 粘贴截图、拖入文件、写入附件、插入相对路径、重名处理、错误恢复 | 中到高；本地存储和异步插入需协调 |
| 图片编辑体验 | 键盘选中、跨图片移动、复制剪切删除、预览、尺寸编辑 | 高；不等同于阅读模式的图片缩放 |
| 公式预览 | 行内/块公式、未闭合公式、语法错误、光标进入时显示源码 | 高；行内替换会影响几何和选区 |
| 公式输入增强 | 命令候选、配对、snippet、Tab 占位符、上下文识别 | 中到高，取决于增强范围 |
| 高级公式输入 | 自动分数、正则片段、矩阵按键、自动括号扩大、用户自定义规则 | 高；更接近独立输入子系统 |
| Markdown 表格 | 预览、Tab/Enter、增删行列、单元格编辑、多行与转义处理 | 高；仅预览并切源码编辑的范围较小 |
| 中文辅助 | 中文括号配对、跳出括号、可选自动空格与标点转换 | 中；规则不能干扰代码、链接和公式 |
| 查找替换 | 编辑内容查找、替换、查找结果定位 | 低到中；不能直接复用依赖阅读 DOM 的查找 |
| 大纲与折叠 | 随输入更新大纲、标题和代码折叠、折叠位置附近编辑 | 中 |
| 链接与路径候选 | 本地文件候选、相对路径、标题建议、wikilink 支持 | 中到高；无 vault 时需要明确候选范围 |
| frontmatter 与扩展语法 | YAML 原文保留、callout、脚注、原始 HTML、Mermaid、不认识的语法 | 中到高；必须区分“不预览”与“不能保存” |
| 模式和标签切换 | 保留草稿、撤销、光标与对应阅读位置 | 高；需要文档会话层 |
| 保存与恢复 | 原子替换、版本校验、自动保存、失败保留草稿、关闭提示或恢复 | 高；是可靠编辑器的基础成本 |
| 多窗口及外部修改 | 同一文件同时编辑，自己的写入不造成循环重载，外部变更不覆盖草稿 | 高 |
| 包体与运行性能 | 延迟加载编辑器，长文输入不重排整篇， inactive 标签资源管理 | 未测；不能从功能数量推算 |

“基础编辑加部分增强”应最终写成上述操作的明确子集。尤其需要避免把“公式自动补全”同时用来指简单命令候选和 LaTeX Suite 全套自动展开。

## 5 社区输入增强的参考价值

### 公式 LaTeX Suite

LaTeX Suite 提供数学上下文片段、Tab 占位符、自动分数、矩阵快捷输入和退出括号等操作。值得先拆成三个层次评估：命令候选；带占位符的固定片段；自动分数和复杂规则。三者的工程成本不同。[项目说明](https://github.com/artisticat1/obsidian-latex-suite)

文档列出的按键优先级涉及自动删除、自动/手动展开、占位符、分数、矩阵和退出公式；这说明不能给每个功能各写一个独立 Tab 监听。自动展开对 IME 的限制也需要考虑。[详细文档](https://github.com/artisticat1/obsidian-latex-suite/blob/main/DOCS.md)

插件本身依赖 Obsidian 与 CodeMirror，并非可直接装入静读的通用库。[依赖声明](https://github.com/artisticat1/obsidian-latex-suite/blob/main/package.json)

进一步核查了其移植项目 Snippetleaf：CodeMirror 子包明确声明目前支持 LaTeX 文档而非 Markdown 文档。这是复用线索，但不能认定“安装后即可补全 Markdown 的 $...$”。仍要适配数学区域识别、语法树和按键优先级。[CodeMirror 子包说明](https://github.com/superle3/snippet-leaf/blob/main/codemirror_extension/README.md)

### 图片 Paste Image Rename

Ob 本身支持粘贴和拖入附件，插件补充的是命名和重名等流程。[Ob 附件说明](https://obsidian.md/help/attachments)、[Paste Image Rename](https://github.com/reorx/obsidian-paste-image-rename)

静读可以内置最常用的附件规则：保存到文档旁的子目录、生成不冲突的名字、插入相对链接。用户自定义复杂模板、批量重命名和自动清理附件应单独计价；不是实现图片插入的必然前提。

必须处理未命名笔记、粘贴过程中切标签、保存失败、同名文件、拖入文件究竟复制还是引用，以及撤销插入与实体图片文件的关系。默认不应因为移除一条引用就删除可能被其他笔记使用的图片。

### 中文 Easy Typing

Easy Typing 的参考能力包括中文括号配对、跳出配对符号、中英文空格、中文标点转换，以及列表和引用里的智能退格/粘贴。[项目说明](https://github.com/Yaozhuwa/easy-typing-obsidian)

对中文学习笔记，配对和列表操作可能有直接价值。自动空格、自动转换标点属于可选偏好，不能当成所有人的默认习惯；必须可关闭、可撤销，并排除代码、URL 和公式等区域。

### 表格 Advanced Tables

Advanced Tables 提供单元格按键导航、格式化及行列操作，还含表格计算等扩展。静读是否需要“直接在表格单元格中写作”应独立讨论，不能因表格预览已有就低估可编辑表格。[项目说明](https://github.com/tgrosinger/advanced-tables-obsidian)

它适合作为操作设计参考。本轮未审计其算法复用边界；如后续考虑复制实现，应另外核查授权和依赖。

### 工具栏 Editing Toolbar

该插件提供常用格式命令的工具栏入口。[项目仓库](https://github.com/PKM-er/obsidian-editing-toolbar)

静读可用一个小工具栏暴露同一套编辑命令。工具栏不是主要技术难点；命令如何正确处理选区、嵌套格式和撤销才是。多套可配置工具栏与复杂文本处理命令不是当前明确需求。

## 6 可复用技术路线

### CodeMirror 6 加定制实时预览

保持编辑文档为 Markdown 字符串，用 decoration 隐藏标记、替换公式或插入图片显示。源码模式关闭相应预览层，仍使用同一个编辑状态。CodeMirror 的官方装饰机制包含 mark、widget、replace、line 等类型；改变块高度的装饰还有布局约束。[官方装饰示例](https://codemirror.net/examples/decoration/)

工程推断：这条路线最贴合“源码保真、光标附近显露语法”和现有阅读器保持原样的要求。需要自有实现或维护预览扩展、Markdown 扩展语法、资源适配及输入增强。成熟文本内核能承担基础编辑，无法替应用解决保存和特殊语法。

### ink-mde

ink-mde 基于 CodeMirror 6，提供混合 Markdown 显示、文件粘贴/拖放回调和图片预览。仓库包含 KaTeX 插件和配置，插件 API 标为 experimental。[项目仓库](https://github.com/davidmyersdev/ink-mde)

需进一步确认：可否访问或保留底层 EditorState；模式切换是否需要重建实例；片段引擎的接入方式；公式与自定义高亮预览；Tauri 本地图片 URL；Markdown 语法覆盖。文件 handler 只是接入点，不能代替本地附件落盘和失败恢复。

### codemirror-live-markdown

该库宣称提供 Ob 风格实时预览，以及可选择的公式、代码、表格、图片和链接模块。[项目仓库](https://github.com/blueberrycongee/codemirror-live-markdown)

核查时 main 分支 package.json 为 0.5.2-alpha.1，这只是仓库声明，不是已核实的最新 npm 发布版本。[package.json](https://github.com/blueberrycongee/codemirror-live-markdown/blob/main/package.json)

其路线图仍有 alpha 阶段描述，callout、脚注等扩展和 advanced IME 等项被列入后续计划。路线图更新时间早于本次调研，不能据此认定当前代码一定不支持；但这足以说明 README 的功能列表不能当作生产成熟度证明。[路线图](https://github.com/blueberrycongee/codemirror-live-markdown/blob/main/ROADMAP.md)

该项目的设计文档明确讨论了拖选时更新装饰导致闪烁和选择中断的问题，可用于定位实时预览的维护难点。[设计文档](https://github.com/blueberrycongee/codemirror-live-markdown/blob/main/CODEMIRROR_LIVE_PREVIEW_DESIGN.md)

### Silkdown

Silkdown 同样宣称基于 CodeMirror 6 实现活动行显露标记，仓库提供 architecture 和 gotchas 文档，涉及 IME、块组件、长文等主题。[项目仓库](https://github.com/magarcia/silkdown)

此次看到的仓库提交历史非常有限，应当作为结构参考或候选，不能仅凭完整文档和 demo 宣称稳定。需要确认发布包、实际维护历史、测试内容和真实用户反馈。

### Vditor

Vditor 提供所见即所得、即时渲染和分屏预览三种模式，有中文文档及图片上传/提示扩展入口。默认存在按需 CDN 加载，可配置资源路径。[项目文档](https://github.com/Vanessa219/vditor)

工程推断：它有机会减少现成编辑界面的搭建，但需要核查即时渲染与源码切换时的 Markdown 往返保真，以及 Lute 与现有 remark 管线的语义差异。桌面产品还要把相关资源本地化，并接管本地文件写入；不能直接使用服务器上传示例。保持现有阅读模式意味着新增编辑管线，而不是替换阅读器。

### Milkdown 和其他富文本内核

Milkdown 基于 ProseMirror 和 remark。[项目说明](https://github.com/Milkdown/milkdown)

工程推断：这类结构化富文本内核适合另一类写作交互，但在本需求中必须先证明 Markdown 源码能按用户期待保留，包括未知语法、frontmatter、彩色嵌套高亮和格式选择。不能把“可以导出 Markdown”等同于“源码模式往返不改变原文”。在证据不足时，不应仅为了好看的可编辑页面选择此路线。

### 继续用 Ob 写作

这是需要认真比较的低自研成本路线。静读继续承担阅读，Ob 处理写作；或者通过主题和设置调整 Ob 阅读效果，减少两款应用切换。

仍需确认外部文件的插件和附件工作流。若能满足，静读自行编辑的主要增益就是更符合用户偏好的统一外观和读写衔接，而不是此前的单文件限制。外部编辑后自动更新，静读已有相应基础行为。

## 7 主要工程难点和容易漏掉的情形

### 预览装饰与输入互相影响

隐藏字符并不会让它们从 Markdown 消失。光标需要能跨过标记、进入和离开公式、选择图片两侧的文字。鼠标拖选、Shift 扩选、Home/End、双击选词、跨块复制都要保持直觉。IME 选词期间 DOM 和选区变动可能破坏输入，应避免在组合输入过程中替换光标附近的内容。

隐藏语法导致行宽变化，公式和图片改变高度，滚动不能反复跳动。活动区域显露语法的粒度也要定义：整行、整段，还是仅格式节点。候选库各自的规则未必与 Ob 一致。

### 文档会话与保存需要成为基础层

建议评估一个按文档管理的会话：原始 Markdown、磁盘基线版本、dirty 状态、EditorState/撤销历史、光标选区、模式和阅读锚点。React 页面只是显示会话，不拥有唯一草稿。否则切标签或模式重建会丢历史。

保存需要重新读取并校验磁盘版本，使用临时文件替换，失败后保留草稿；自己的写入与外部变化应可区分。多窗口同时 dirty 时要有明确处理。仅把高亮备份方式照搬成每次自动保存都复制整篇文章，会带来磁盘和备份管理成本。

### 阅读高亮与未保存稿的交互

阅读模式现在会直接把标记写入文件。若切回阅读时显示尚未落盘的稿件，再执行高亮就出现新的状态组合：高亮写到哪一版？随后撤销编辑是否撤销高亮？其他窗口更新的高亮如何同步？

需要选择统一编辑事务、切回阅读前完成保存，或另一个明确的产品规则。规则必须在实现前确定，不能靠读写两套状态偶然同步。

### 公式显示和公式输入是两套成本

静读使用 KaTeX；Ob 的数学显示使用 MathJax。[Ob 数学说明](https://obsidian.md/help/advanced-syntax)

操作对标不要求渲染器完全相同，但支持的命令、宏和错误行为需要明确。片段应生成当前渲染器可处理的语法。数学环境识别还要排除代码块、转义美元、普通货币文本和未闭合公式。正则片段和自动分数不能仅靠上一字符判断。

一个 LaTeX 文档补全包处理整篇数学文档，不等于能正确处理中文 Markdown 中局部的数学区域。大量自动转换也会扩大撤销和按键冲突问题。

### 附件插入属于文件事务

异步存储结束时用户可能已移动光标、撤销、切标签或关闭笔记，插入位置必须跟随文档变更映射。文件写成但引用没有插入、引用插入但文件没写成，都需要恢复规则。

未保存笔记没有可用于解析相对路径的稳定目录；应明确首次插图是否要求选择保存位置。Windows 文件名、空格、中文路径、跨盘引用、复制和移动文档后的附件关系都需要处理。不能默认开启远程图片自动下载而绕过现有访问规则。

### 格式命令和按键需要同一套规则

Tab 在列表缩进、代码缩进、公式片段、括号跳出、表格和候选框之间需要有上下文优先级。Enter 也涉及段落、列表、引用、矩阵和补全确认。键盘可访问性还要求用户能退出编辑区，而不是永远被 Tab 捕获。

粘贴内容需要区分纯文本、HTML、图片和文件。格式转换、智能粘贴、补全和图片引用插入应正确归入撤销事务，不能让一次撤销回到不完整状态。

### 原文保真与两套语法解释

阅读器与编辑器可能分别使用 remark 和 Lezer/Lute/ProseMirror，扩展能力和未闭合语法处理不同。静读的彩色嵌套高亮属于扩展，并不能保证 Ob 或通用编辑库按同样方式显示。保持字节或文本不损坏，与保证所有预览一致，是两个独立目标。

源码偏移还存在 Rust UTF-8 字节、JavaScript UTF-16 code unit、emoji 和 CRLF 的区别。已有高亮偏移映射只能为特定操作提供依据，不自动构成完整编辑器位置映射。

### 长文和跨平台支持会持续消耗维护时间

每次输入不应整篇 parse、渲染 KaTeX/Mermaid 或刷新 ReactMarkdown 阅读树。可按变更范围处理，缓存公式，避免重复渲染非活动区域。编辑内核虚拟化后大纲、搜索、块预览和阅读定位的协同也要考虑。

浏览器 demo 不等于 WebView2/WKWebView 行为；中文输入法、剪贴板、拖放、系统快捷键和弹出窗口要分别验收。自动化覆盖能减少回归，但不能替代长时间实际写作。

## 8 如何讨论是否太重

应把“重”拆为四项，避免仅数功能按钮：

| 维度 | 需要回答的问题 |
| --- | --- |
| 一次性开发 | 宿主适配、语法扩展、会话层、保存、增强输入分别需要多少工作？ |
| 长期维护 | 库升级后哪些组件受影响？谁维护中文输入、选区和特殊块的边界？ |
| 运行与分发 | 实际增加多少本地资源、初始化时间、输入延迟和内存？能否延迟加载？ |
| 用户认知 | 是否增加设置负担、附件位置规则和模式切换负担？ |

本轮没有性能或包体测量，不提供 MB、毫秒或“几天能做完”的数字。功能精简不能自动保证可靠，采用成熟库也不能自动保证轻量。维护复杂度可能比包体更早成为限制。

请 GPT Pro 分别估算三档，不要用最低档的成本回答完整目标：

| 档位 | 范围 | 作用 |
| --- | --- | --- |
| 对照档 | 保留阅读；普通源码编辑；可靠保存；基础图片插入 | 估计最基本集成成本，不代表满足用户日常写作目标 |
| 目标档 | 阅读/编辑/源码；常用 Markdown 实时预览；图片；固定公式片段和 Tab 跳转；基本中文辅助；可靠会话和保存 | 最接近当前需求，具体能力仍待确认 |
| 深度对标档 | 目标档加直接编辑表格、复杂图片交互、自动分数和矩阵规则、灵活自定义输入转换及更多扩展语法 | 可能成为长期编辑器维护项目 |

现阶段没有证据支持“目标档很轻松”。也没有证据证明它必然过重。值得先由架构评审确认可复用比例、不可省略的宿主成本和高风险项，再决定是否投入开发。

## 9 给 GPT Pro 的具体评审问题

1. 按目标档和深度对标档分别评估，哪些能力由内核提供，哪些必须自研？请列出接口和状态，而不是只说使用某个库。
2. CodeMirror 定制、ink-mde、Vditor 与富文本路线，在源码保真、Ob 风格交互、公式增强、Tauri 适配和长期维护方面各有什么成本？
3. 现成实时预览扩展处于什么成熟度？alpha 标记、文档与实际代码差异、IME 与长文测试能说明什么，不能说明什么？
4. Snippetleaf 只支持 LaTeX 文档的限制需要怎样适配？最小的数学上下文 snippet 系统能否避免承担全套 LaTeX Suite 的复杂度？
5. ReaderWorkspace 重建页面、external-change 直接重载、write_file_highlights 限定语法变化，这三处分别需要怎样重构？
6. 编辑草稿切到阅读后做高亮，怎样避免两套写入状态冲突并保持撤销一致？
7. 附件插入、自动保存、外部修改、多窗口冲突和恢复的最小可靠架构是什么？哪些成本无法通过削减工具栏省掉？
8. 给出一次性开发与后续维护的乐观、常见和悲观区间，说明人员经验、库复用程度、平台和质量标准等假设；无法估算的地方明确列出缺失证据。
9. 哪些缺失证据可通过文档和静态源码进一步解决，哪些必须通过实际输入与长期写作解决？不要将短期 demo 成功当成发布依据。
10. 考虑 Ob 1.14 已支持外部文件后，自行开发的实际增益是否足以覆盖成本？请认真比较继续自研、只做辅助编辑、Ob 写作加静读阅读、直接使用 Ob 四条路线。

## 10 决策时应保留的选项

继续自研的理由应落在用户实际收益：更喜欢的排版、原目录就地写作、阅读高亮与笔记写作衔接，以及恰好适合自己的数学和图片输入方式。只有这些收益明确且维护可控，才值得推进。

如果达到舒服的写作体验需要长期维护大量实时预览边界，采用 Ob 写作是合理选择；静读仍可作为阅读器保留。Ob 是否能完全替代静读，需要另外比较主题排版、目录浏览、搜索和高亮扩展，不能仅从单文件支持得出结论。

辅助源码编辑与用户提出的日常编辑目标应分别评估，不能用前者的较低成本代替后者的难度。下一步决策依据应是实现成本、长期维护责任和实际收益。
